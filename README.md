03 — Clonar o Repositório e Criar uma Branch

Cada membro do time deve executar essa etapa individualmente.

Clonar o repositório:
bash
   git clone <URL_DO_REPOSITORIO>
   cd conectapet
Criar uma branch a partir da main, com um nome que identifique sua parte. Sugestão de padrão:
   secao/nome-da-secao-seu-nome

Exemplo (Matheus cuidando da Introdução):

bash
   git checkout -b secao/introducao-matheus

Cada pessoa deve trabalhar apenas na sua própria branch, referente à sua seção do README.

04 — Fazer no Mínimo 3 Commits

⚠️ Requisito obrigatório: cada integrante deve realizar no mínimo 3 commits em sua branch antes de abrir o Pull Request. Isso é essencial para praticar o versionamento incremental (não vale fazer tudo em um único commit).

Sugestão de divisão dos 3 commits (pode variar):

Commit 1: Criação do arquivo/estrutura inicial da seção.
Commit 2: Adição do conteúdo principal da seção.
Commit 3: Revisão, ajustes de formatação e finalização do texto.

Exemplo de comandos:

bash
git add .
git commit -m "docs: cria estrutura inicial da seção de introdução"

# ... mais alterações ...
git add .
git commit -m "docs: adiciona conteúdo principal da introdução"

# ... ajustes finais ...
git add .
git commit -m "docs: revisa e finaliza texto da introdução"

Use mensagens de commit claras e descritivas, mesmo em um projeto fictício — isso é parte do treino.

05 — Enviar a Branch e Abrir o Pull Request (PR)
Enviar (push) a branch para o repositório remoto:
bash
   git push origin secao/introducao-matheus
No GitHub, abrir um Pull Request da sua branch para a main:
Título claro, indicando a seção trabalhada.
Descrição breve do que foi feito.
Marcar como revisor(a) um outro integrante do time (não pode revisar o próprio PR).
06 — Revisar o Pull Request de Outro Integrante

Cada membro deve revisar o PR de pelo menos um colega, seguindo as boas práticas:

Ler o conteúdo adicionado com atenção.
Deixar comentários construtivos (sugestões, correções de texto, dúvidas).
Aprovar o PR (Approve) ou solicitar alterações (Request changes), se necessário.
Se solicitar alterações, o autor deve corrigir e o revisor deve validar novamente antes do merge.
